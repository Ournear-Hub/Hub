Commit: *(recorded in Git snapshot after the A.6 commit)*  
Message: `feat: implement v1.1 replacements lifecycle`

A.6 starts only from a joined employee:

Employee (Joined placement) → Replacement Case → new Application → existing Screening/Shortlist/Submission/Placement/Offer/Joining → new Employee

The original employee and original placement are historical records and are never overwritten.

- Requested

Replacement status is independent of Application, Submission, Placement, Offer, Joining, and Employee status.

- Employee left

### Admin UX

- `/admin/replacements` hybrid workspace (list, search, filters, drawer, timeline)
- Sidebar: Replacements enabled
- Employee drawer: Replacement tab + Request replacement
- Placement drawer: Replacement tab (original vs replacement placement context)

### Models / services / controllers

- `Replacement`
- `ReplacementService` (`request`, `identifyApplication`, `cancel`, `syncSubmissionCreated`, `syncPlacementCreated`, `syncEmployeeJoined`)
- `ReplacementsController`
- `ReplacementQuery`
- `ReplacementPolicy` (admin `canManageRecruitment` only)
- `PlacementService` and `EmployerSubmissionService` call replacement sync hooks
- Existing Application / Submission / Placement / Offer / Joining / Employee workflow reused

### Business rules implemented

1. Only a joined employee (placement status Joined, complete employer/job/application/submission lineage) can create a replacement.
2. Original employee, original placement, and original application/submission are retained and never overwritten.
3. Replacement belongs to the original employer + job. Historical jobs are not reactivated.
4. Replacement candidate must be a different application for the original job, and must be shortlisted or already submitted for that employer/job.
5. Replacement candidate continues through existing Application → Submit → Select → Place → Offer → Join.
6. Replacement placement is a new Placement. Original placement is untouched.
7. Replacement employee is a new Employee. Original employee is untouched.
8. Replacement is marked Completed only after the replacement employee has joined.
9. At most one open replacement per original employee. After Completed, the next replacement must start from the current joined employee.
10. A live (non-declined/non-withdrawn) replacement placement blocks changing the identified candidate. After decline/withdraw, another eligible application may be identified. Previous attempts are not stored as a separate attempts table.

## A.7 — Payments / Finance

Commit: *(recorded in Git snapshot after the A.7 commit)*  
Message: `feat: implement v1.1 payments finance lifecycle`

A.7 is recruitment billing, not an accounting/ERP system.

Billable recruitment event
→ Draft invoice
→ Issued invoice
→ Payment due
→ Payment received (partial or full)
→ Paid / reconciled

Joining is **not** payment received. An invoice is created manually by an admin after the employee has joined.

### Database

Additive migration `2026_09_20_200000_add_invoices_and_payments.php`:

- `invoices` — employer/job/application/submission/placement/employee FKs; nullable `replacement_id`; status; currency INR; amount; gst_rate; gst_amount; total_amount; billed_at; due_at; issued_at; cancelled_at; notes; created_by
- `payments` — invoice + employer FKs; currency; amount received; paid_at; method; reference; notes; recorded_by
- `recruitment_activities.invoice_id` and `payment_id` nullable FKs
- `business_id_sequences` insertOrIgnore for `ONT-I` and `ONT-M`

Invoice and payment are separate tables. Historical billed amounts are stored on the invoice and are not recalculated from later pricing.

### Business IDs

- Invoice: `ONT-I-000001`
- Payment: `ONT-M-000001` (`ONT-P` is Placement)
- Uses existing `HasBusinessId` + `BusinessIdGenerator`

### Invoice status (single A.7 invoice status system)

- Draft
- Issued
- Partially Paid
- Paid
- Cancelled

Overdue is computed (Issued or Partially Paid and `due_at` before today). It is not a stored status.

Payment records represent money received. They do not have a competing payment-status machine.

### Currency / GST

- Currency is explicit `INR` on each invoice and payment.
- GST fields are optional snapshots (`gst_rate`, `gst_amount`, `total_amount`). Default rate is 0.
- No tax engine, GST returns, or TDS.

### Admin UX

- `/admin/finance` hybrid workspace (invoice list, search, filters, summary cards, recent payments, drawer)
- Sidebar: Payments enabled
- Employer drawer: Finance tab (billed / received / outstanding / overdue, invoices, recent payments)
- Placement drawer: Finance tab (invoice context; placement is not an invoice)
- Employee drawer: Finance tab + Create invoice (recruitment fee, not salary)

### Models / services / controllers

- `Invoice`, `Payment`
- `Money` helper (BCMath, 2 decimal places)
- `FinanceService` (`createInvoice`, `issue`, `cancel`, `recordPayment`)
- `FinanceController`
- `FinanceQuery`
- `InvoicePolicy` (admin `canManageRecruitment` only)
- Create / issue / cancel / record-payment form requests

### Business rules implemented

1. Billable event = Joined employee (placement status Joined, complete employer/job/application/submission lineage). Submission, selection, placement, offer, and joining confirmation are not billable by themselves.
2. Joining does not auto-create an invoice or a payment.
3. Admin creates a Draft invoice from the employee record. Issuing freezes the billed amount/GST/total.
4. One active (non-cancelled) invoice per employee. A cancelled invoice may be replaced.
5. Due date is stored on the invoice and is not recalculated from later payment-term settings.
6. Partial payments are supported. The invoice is Paid only when received amount satisfies the stored total. Overpayment is rejected.
7. Cancel is allowed for Draft, or Issued with zero payments. Payments already recorded block cancellation. No silent amount overwrite; no credit-note system.
8. Employer finance totals count Issued / Partially Paid / Paid invoices only. Draft and Cancelled are excluded from billed/received/outstanding.
9. Replacement is not auto-billed and is not assumed free. Original invoices remain historical. A replacement employee may be invoiced manually; that invoice stores `replacement_id`.
10. No fee schedule or employer-specific pricing master. The agreed amount is entered on the invoice.

## A.8 — Notifications + Messages

Commit: *(recorded in Git snapshot after the A.8 commit)*  
Message: `feat: implement v1.1 notifications messaging`

A.8 is a communication layer beside existing workflows. It does not introduce a second recruitment or finance status system.

### Notifications

Laravel database notifications (`notifications` table, `Notifiable` on `User`). Channel: `database` only.

Recipients: existing Admin users (`role = admin`). Candidate and employer accounts are not in-app recipients because those portals are not implemented.

Existing operational mail (`RecruitmentNotificationService`, `SubmissionMailService`) is unchanged. A.8 does not add new mailables or a queue architecture.

Triggers are called from domain services after state-changing actions (`AdminAlertService` + `DB::afterCommit`). GET/index pages never create notifications.

Supported Admin in-app events:

- Application received
- Candidate shortlisted
- Employer submission created
- Employer selected / rejected
- Placement created
- Offer created / accepted / declined
- Joining confirmed
- Employee joined
- Replacement requested / candidate identified / completed / cancelled
- Invoice issued / cancelled
- Payment recorded

Deferred as no valid current in-app recipient, or already covered by another event:

- Candidate/employer portal notifications
- Replacement selected (covered by employer selected)
- Replacement joined as a separate event (covered by employee joined + replacement completed)
- Automated overdue invoice reminders
- Interview / application-status email duplication

### Messages

Separate from notifications.

- `conversations` + `conversation_participants` + `messages`
- Admin-to-Admin only
- Optional related context (employer, job, application, submission, placement, employee, replacement, invoice)
- Messages are not deleted by ordinary UI actions
- Opening a thread marks it read for that Admin

Email is a delivery channel for existing operational mail. It is not the source of truth for notifications or messages.

### Database

Additive migration `2026_09_20_210000_add_notifications_and_messages.php`:

- `notifications` — Laravel database notifications
- `conversations`
- `conversation_participants` (`last_read_at`, `last_read_message_id`)
- `messages`

### Models / services / controllers

- `LifecycleNotification`
- `AdminAlertService`
- `Conversation`, `ConversationParticipant`, `Message`
- `MessageService`
- `NotificationsController`, `MessagesController`
- `NotificationQuery`, `ConversationQuery`

### Admin UX

- Sidebar Communication: Notifications and Messages enabled
- Top bar unread badge + recent notification panel
- `/admin/notifications` hybrid workspace (list, unread filter, mark read/unread/all, open related record)
- `/admin/messages` hybrid workspace (compose, thread drawer, reply)

### Business rules implemented

1. Notifications and messages do not change application, submission, placement, replacement, invoice, or payment status.
2. In-app notifications go only to Admin users who already exist.
3. Missing Admin recipients or notification storage failure does not block recruitment actions.
4. Duplicate fingerprints are not stored twice.
5. Reading a notification only updates `read_at`.
6. In-app messages cannot be sent to candidate or employer accounts in A.8.
7. Recruitment activities remain the historical event log and are not replaced.

## Important architecture rules

### Production safety

- Never rebuild V1.
- Preserve existing production data.
- Prefer additive migrations.
- Do not remove existing columns without an explicit migration plan.
- Do not silently reinterpret historical data.
- Do not run new migrations against production until an explicit production deploy step.

### Database naming

CRITICAL:

- Recruitment listing table = `job_listings`
- Laravel queue table = `jobs`

Never rename or confuse them.

### Guest applications

`applications.user_id` remains nullable.

Guest applications are a supported V1 workflow.

### Statuses

Do not rename existing V1 status strings/enums without explicit migration planning.

Keep these concepts distinct:

- Application status
- Screening decision
- Submission status
- Employer decision
- Placement / joining (A.5)
- Replacement (A.6)
- Invoice status (A.7)
- Payment received (A.7)
- Notification read/unread (A.8)
- Message read/unread (A.8)

### Business IDs

Business IDs are separate from numeric primary keys.

Never regenerate them.

Use the existing A.1 `BusinessIdGenerator`. Do not create a second generator.

Current prefixes:

- Candidate `ONT-C`
- Job `ONT-J`
- Application `ONT-A`
- Employer `ONT-E`
- Placement: `ONT-P`
- Employee: `ONT-W`
- Replacement: `ONT-R`
- Invoice: `ONT-I`
- Payment: `ONT-M`

### Master data

Master data should be used for new structured records while legacy strings remain compatible where required.

Do not treat V1 `job_listings.category` Permanent/Contract/Temporary as Job Category.

### Employer selection

Employer selection is submission-level, not global candidate-level.

The same candidate may have multiple applications. Selection stays tied to the specific employer / job / submission.

### Placement

Placement must originate from a specific selected employer submission.

### Replacement

A replacement must originate from a joined employee / placement. Never overwrite the original employee or original placement. The replacement candidate uses a new recruitment path.

### Finance

Recruitment billing is a client invoice against a joined employee. It is not employee salary and not a payment-received event.

Do not recalculate historical invoice amounts from later pricing. Do not treat joining as payment received. Do not auto-charge replacements unless a later phase defines a contractual entitlement/fee rule.

### Communication

Notifications are Admin alerts. Messages are human-authored conversations. Recruitment activities remain the historical event log. Email is a delivery channel for existing operational mail and is not the source of truth for A.8 records.

Do not send in-app messages or notifications to candidate/employer portal accounts until those portals exist.

### Authorization

New recruitment workspaces are admin-only unless a later phase explicitly changes this.

Do not enable recruiter access yet.

Do not implement full RBAC yet.

Do not expose Admin functionality to employer accounts or candidates.

### Admin UX

Reuse A.0 components and the hybrid workspace pattern (Jobs, Candidates, Applications, Screening, Shortlisted, Employers, Employer Submissions).

Preserve query-string state when opening/closing drawers.

### Testing / deploy notes

- Tests use SQLite `:memory:`
- Do not test against production MySQL
- Do not spend time fixing unrelated Pint failures unless asked
- Targeted tests first, then the existing full suite, TypeScript, and Vite build for phase work

## Current known limitations

Do not fix these automatically unless the relevant future phase requires it.

1. Existing jobs may be unassigned to employers.
2. Existing V1 shortlisted records may not have `shortlisted_at`.
3. Candidate resumes are currently application-based rather than profile-level.
4. Public job filters still contain legacy string behavior.
5. Employer `Under Review` exists but currently has no separate action.
6. Employer submission resubmission after rejection is currently blocked by design.
7. Production migrations have not been run for the newly added A.3/A.4/A.5/A.6/A.7/A.8 tables/columns.
8. V1 mail remains synchronous.
9. Full RBAC is not yet implemented.
10. Recruiter access is not yet enabled.

Additional A.4 operational notes:

- Guest enquiries without a matching employer `user_id` remain in Employer Enquiries and are not forced into the Employer workspace.
- Existing employer account login/enquiry functionality continues; A.4 did not build an employer portal.
- A selected submission is the intended input to A.5; ApplicationStatus is not auto-moved to Selected.

Additional A.5 operational notes:

- Existing selected submissions do not automatically become placements; an admin must create the placement.
- Offer salary/CTC is optional and stored on `placement_offers`; it is not copied from `job_listings.salary`.
- Declined/withdrawn placements cannot be re-offered in A.5.
- Employee business IDs use `ONT-W` because `ONT-E` is Employer.
- ApplicationStatus::Placed still exists in V1 and is not auto-set when an employee joins.

Additional A.6 operational notes:

- Replacement is requested from a joined employee, not from a candidate, application, submission, or unjoined placement.
- The replacement candidate pointer is the current attempt only. Identifying another application after a declined/withdrawn replacement placement replaces that pointer; previous applications remain in recruitment history.
- A completed original employee cannot start another replacement; the next case starts from the current joined replacement employee.
- Inactive original jobs are not reactivated. The replacement still references the historical job.
- Replacement reasons are enum strings, not master data.

Additional A.7 operational notes:

- Billing is available only after joining. Admin must create and issue the invoice; joining does not create finance records.
- Invoice amounts/GST/totals are snapshots. There is no fee schedule.
- Overdue is computed from due date + open invoice status. It is not stored.
- GST fields exist as optional snapshots. There is no GST filing or rate master.
- Replacement entitlement / free-replacement period is not implemented. Replacement invoices are manual.
- Payment recording is manual. There is no payment gateway.

Additional A.8 operational notes:

- In-app notifications are Admin-only. Candidate/employer users have accounts but no notification inbox in A.8.
- Existing application/enquiry/interview emails remain the operational mail path. A.8 did not add new mailables.
- V1 mailables still implement ShouldQueue; A.8 did not introduce a new queue worker architecture. Tests continue to use `QUEUE_CONNECTION=sync`.
- Admin-to-Admin messages only. No candidate/employer/recruiter chat.
- Notifications are retained indefinitely; no archival policy yet.
